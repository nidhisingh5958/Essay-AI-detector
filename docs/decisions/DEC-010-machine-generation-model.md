# DEC-010 — Machine Text Generation Model

## Status
Provisional

## Date
2026-08-10

## Context

Phase 5B needs a model to (a) generate fully machine-written essay
counterparts to human seed essays, and (b) perform the AI-polishing/
rewriting operations that create mixed samples (DEC-011). This is a
different job than [DEC-007](DEC-007-local-language-model-choice.md)'s
`distilgpt2`: that model is a plain causal LM used only to *measure*
token probabilities (per [DEC-004](DEC-004-no-llm-classifier.md)), not to
follow instructions like "write an essay about X" or "lightly polish this
paragraph without changing its meaning." Generation needs genuine
instruction-following ability; `distilgpt2` has none.

## Problem

Which model should generate the machine-written and AI-polished/rewritten
samples?

## Alternatives Considered

### Alternative A: Reuse `distilgpt2` (the detection instrument)
Advantages: no new dependency.
Disadvantages: not instruction-tuned — it can only continue text, not
reliably follow "write an essay about this prompt" or "rewrite this
sentence, preserve its meaning." Also explicitly discouraged: using the
same model for generation and detection risks the detector merely
learning that one model's continuation statistics rather than anything
generalizable, and the brief's own guidance for this phase says not to
default to the detection model. Rejected.

### Alternative B: Hosted API (e.g. GPT-4o-mini, Claude Haiku, Gemini
Flash)
Advantages: highest instruction-following quality and diversity of any
option considered; would produce the most realistic "polish" and
"rewrite" behavior with the least prompt-engineering effort.
Disadvantages: costs money per call at dataset scale (thousands of
essays × multiple transformation categories); requires network access and
an API key not present in this environment; server-side model versions
can change over time, weakening exact reproducibility of "what generated
this sample" months later; and it cuts against this project's consistent
local-first posture (DEC-004, DEC-007, DEC-008). Not selected as the
*primary* generator — but see "Revisit When": reserved as a candidate for
a specific, bounded future use (a held-out generalization-test slice
generated by a model never used in training generation).

### Alternative C: A larger local model (e.g. Mistral-7B-Instruct,
Llama-3.1-8B-Instruct)
Advantages: better quality/coherence than smaller instruction models.
Disadvantages: 5-10x the parameters of the models in Alternative D below;
CPU-only generation at that size is slow enough to make even a modest
pilot (tens of essays) a multi-hour undertaking, and this environment has
no confirmed GPU. Also, Llama-family licenses carry usage-restriction
clauses (e.g. conditions on very-large-scale commercial deployment) that
are irrelevant at this project's scale but add unnecessary license
review overhead compared to Apache-2.0/MIT alternatives. Not selected now;
noted as an escalation path if a GPU becomes available and small-model
quality proves insufficient.

### Alternative D: A small, local, instruction-tuned model
Candidates actually compared:

- **Qwen2.5-1.5B-Instruct** (Alibaba) — confirmed via Hugging Face:
  **Apache-2.0** license, 1.5B parameters. Small enough for CPU
  generation at pilot scale in reasonable time; permissively licensed
  (no usage-restriction clauses to review).
- **Phi-3.5-mini-instruct** (Microsoft) — confirmed via Hugging Face:
  **MIT** license, 3.8B parameters. Generally regarded as strong for its
  size on instruction-following/reasoning tasks, at the cost of being
  ~2.5x larger (slower on CPU) than Qwen2.5-1.5B-Instruct.
- **TinyLlama-1.1B-Chat** — smaller still, but weaker instruction-
  following in practice than either of the above; more prone to drifting
  off-instruction on tasks like "rewrite only this sentence, keep the
  rest unchanged," which this project's surgical-splice mixed-sample
  mechanic (DEC-011) depends on being followed precisely. Not selected.
- **Gemma-2-2b-it** (Google) — viable middle ground, but no clear
  advantage found over Qwen2.5-1.5B-Instruct for this task, and Gemma's
  license includes use-restriction terms (a "prohibited uses" policy)
  that add review overhead Apache-2.0 doesn't.

Advantages of this category generally: local, no per-call cost, no
network dependency once downloaded, fully reproducible given a pinned
model revision + fixed generation config/seed.

Disadvantages of this category generally: weaker instruction-following
and lower output diversity/quality than a frontier hosted model — a real,
documented limitation of every sample this pipeline produces, not
something to paper over in `docs/dataset.md`.

## Decision

Use **Qwen2.5-1.5B-Instruct** (Apache-2.0, 1.5B parameters) as the
primary local generation model for both full-essay generation and the
AI-polishing/rewriting operations behind mixed samples (DEC-011).
**Phi-3.5-mini-instruct** (MIT, 3.8B) is the documented escalation path if
the pilot (EXP-DATA-001) shows Qwen2.5-1.5B-Instruct's output quality or
instruction adherence is insufficient — the same "smaller-first,
same-family-tokenizer-not-guaranteed-but-drop-in-via-shared-interface"
pattern used in DEC-007.

## Why

Between all alternatives, this is the only option that is simultaneously:
local (no paid API, no network dependency after download), genuinely
instruction-tuned (unlike `distilgpt2`), small enough for CPU-only
generation at pilot scale in reasonable time, and permissively licensed
with no usage-restriction clauses requiring further review.

## Evidence

**Smoke-tested, not pilot-validated.** After this record was first
written, the model was downloaded (2.9GB, cached under
`~/.cache/huggingface/hub/models--Qwen--Qwen2.5-1.5B-Instruct`) and
loaded in this environment: confirmed 1,543,714,304 parameters and a
present chat template (`apply_chat_template` works). Two smoke-test
generations were run on CPU, at explicit user request, kept deliberately
smaller in scope than the EXP-DATA-001 pilot:

1. **Surgical-splice-style sentence rewrite** — instructed to rewrite one
   sentence only, no preamble, return only the result. Output: clean,
   no preamble/instruction leakage, meaning preserved
   ("Volunteering at the animal shelter taught me the importance of
   patience and quiet persistence." → "Being involved in volunteering at
   the animal shelter helped me understand the value of being patient
   and persistent."). ~10s on CPU.
2. **Short full-essay generation** — asked for a ~120-word persuasive
   essay on a sample prompt. Output was on-topic, coherently structured
   (three supporting reasons), with no instruction leakage — but ran to
   186+ words before hitting the `max_new_tokens` cutoff rather than
   respecting the requested ~120-word target. ~37s on CPU for ~250
   generated tokens (roughly 6-7 tokens/sec on this CPU, useful for
   estimating full-pilot/full-dataset generation time).

**New finding, feeding back into methodology:** an in-instruction length
request ("approximately N words") is not sufficient on its own to control
output length with this model — see
[generation-methodology.md](../generation-methodology.md) Section 5,
updated to note that length control needs an explicit mechanism (tighter
`max_new_tokens` budgeting and/or post-hoc truncation to the nearest
sentence boundary near the target), not just a phrased request.

**EXP-DATA-001 pilot, executed 2026-08-10** (60 real samples; full
report: [reports/EXP-DATA-001.md](../../reports/EXP-DATA-001.md)):
model quality itself was **good** for full-essay generation (7/10 passed
QC cleanly, the other 3 only flagged by an unrelated QC check bug — see
DEC-011's Evidence) and for the surgical-splice rewrite categories
(6/10 and 9/10 passed cleanly). Zero near-duplicates across 10 full_ai
generations. The categories that failed heavily (`light_polish`/
`moderate_polish`, 70% structure-drift) are **not attributed to this
model's quality** in isolation — the pilot could not distinguish "model
can't do this" from "the whole-essay-instruction methodology doesn't fit
what any model of this size will reliably do" (DEC-011's revisit plan
calls for testing a methodology fix before concluding the model needs to
change). Status stays **Provisional**: the model choice is validated for
full-generation and surgical-splice use; it is not yet validated (or
ruled out) for the polish categories specifically.

## Trade-offs

Accepting a smaller, weaker instruction-follower than a hosted frontier
model, in exchange for zero cost, full local reproducibility, and
consistency with every other model-choice decision this project has made
(DEC-004, DEC-007, DEC-008).

## Consequences

Positive:
- No API cost or key management for dataset generation.
- Exact reproducibility: pinned model revision + logged generation config
  (temperature, top_p, seed) fully determines output, unlike a hosted
  model whose server-side version can change.

Negative:
- Generated essays and rewrites will likely be less diverse and less
  sophisticated than what a frontier hosted model would produce — this is
  a real limitation of the resulting dataset, to be stated in
  `docs/dataset.md` and considered when interpreting any later evaluation
  result (a detector that performs well against Qwen2.5-1.5B-Instruct-
  generated text has not been shown to generalize to essays polished by
  e.g. GPT-4-class tools, which are what students realistically have
  access to).

## Revisit When

1. EXP-DATA-001 (pilot) runs and shows Qwen2.5-1.5B-Instruct fails to
   follow the surgical rewrite instructions precisely enough (e.g.
   frequently rewrites more than the targeted sentence, or produces
   visible instruction-following artifacts like "Here is the rewritten
   sentence:") — escalate to Phi-3.5-mini-instruct first, per the
   documented path above, before considering a hosted API.
2. Per Section 17 of the project brief: once a detector actually exists
   (Phase 6+) and has been evaluated against Qwen2.5-1.5B-Instruct-
   generated data, consider generating a **held-out evaluation-only**
   slice using a hosted API model that was never used during generation-
   pipeline development, specifically to test whether the detector
   learned generalizable signal or just this one small model's
   generation quirks. This is a future evaluation consideration, not
   something to implement now — recorded here so it isn't forgotten, per
   explicit instruction not to implement it prematurely.
