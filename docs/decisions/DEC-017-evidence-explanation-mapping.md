# DEC-017 — Evidence/Explanation Mapping Design

## Status
Provisional (design-only — no explanation system has been implemented
or run yet)

## Date
2026-08-15

## Context

The project's master mandate is explicit: a detector must show
**evidence**, not an opaque verdict — and per DEC-004, a chat/LLM model
must never be the thing producing that evidence after the fact (that
would silently reintroduce the "ask an LLM if this is AI" pattern this
whole project exists to avoid). Every user-facing explanation must trace
back to an actual computed feature value, deterministically.

## Problem

How does a raw feature vector and a model decision become a human-
readable explanation, without ever using a generative model to write
that explanation, and without ever asserting an explanation the
measured features don't actually support?

## Alternatives Considered

### Alternative A — Post-hoc LLM-generated natural-language explanation
("summarize why this was flagged").
Rejected outright, not just deprioritized. This is exactly the pattern
DEC-004 forbids: an LLM producing the user-facing judgment/explanation,
un-auditable against the actual feature values, and capable of
confabulating a plausible-sounding reason that doesn't match what the
detector logic actually weighed. No amount of prompt engineering fixes
this — the LLM would still be the thing deciding what to say, not the
measured features.

### Alternative B — Show raw feature values and coefficients directly,
with no natural-language layer.
Advantages: maximally faithful, zero risk of overstatement.
Disadvantages: not usable by the brief's actual audience (a student or
reviewer needs to understand "why," not read a coefficient table) — the
brief explicitly wants human-readable evidence, not a raw feature dump.

### Alternative C (chosen) — A fixed, deterministic template layer:
each feature (or small group of related features) has a pre-written,
human-readable evidence-statement template; the template is filled in
using the feature's actual computed value and its relative
position — never generated by a model call.
Advantages: every explanation is reproducible from the feature values
alone (re-running the same essay through the same model produces the
same explanation, byte for byte); satisfies the "deterministic where
practical" requirement directly; keeps DEC-004's constraint intact —
the explanation is data, not model output.
Disadvantages: template coverage is finite — a feature with no
pre-written template produces no explanation for that dimension, rather
than an improvised one. Accepted: an incomplete-but-honest explanation
set is preferred over a complete-but-fabricated one.

## Decision

**Evidence pipeline**:

```
feature value (already computed, e.g. mean_log_prob = -3.2)
        |
        v
normalized/relative measurement
  (e.g. z-score or percentile against the TRAIN split's
   per-class or overall distribution -- computed once, stored,
   not recomputed ad hoc per request)
        |
        v
evidence statement
  (fixed template keyed to the feature, filled in with the
   normalized value and, where relevant, a plain-language
   direction -- "higher than typical," "within typical range" --
   itself derived from the normalized value via a fixed rule,
   not asserted)
```

**Concrete mapping examples** (illustrative — the exact template wording
is an implementation detail, not fixed by this decision):
- `mean_log_prob` / `perplexity` → "This sentence's wording is
  [more/less/typically] predictable to the reference language model
  than [X%] of sentences in this essay's class." — bound directly to
  the measured value, not an assertion that predictability implies
  authorship (per DEC-013 of methodology.md's standing warning).
- `predictability_delta` → "Predictability shifts by [value] compared
  to the previous sentence, [more/less] than typical." — the actual
  DEC-004-anticipated "neighboring-sentence predictability change"
  signal, named explicitly rather than left implicit.
- `sentence_length_cv` / rhythm features → "Sentence-length variation
  in this essay is [higher/lower/typical] compared to reference."
- Every evidence statement **states the feature, the measured value,
  and the comparison basis** — never a bare conclusion ("this is
  AI-written") without the measurement that produced it.

**Hard rule**: no explanation text is ever produced by a call to a
generative/chat model, at classification time or afterward. Every
template is fixed, versioned code, reviewable independently of any
specific essay's output.

## Why

This is the direct, concrete implementation of DEC-004's architectural
constraint at the explanation layer specifically — the same constraint
that already governs the classification decision itself must also
govern the explanation of that decision, or the constraint is only
half-applied.

## Evidence

**First real applications, 2026-08-15**: EXP-003A (2 worked examples,
essay-level) and EXP-003B (2 worked examples, sentence-level) both
applied this template-based mapping to real frozen-test-run cases — see
[reports/EXP-003A.md](../../reports/EXP-003A.md) §14 and
[reports/EXP-003B.md](../../reports/EXP-003B.md) §13. All four
statements were generated from stored feature values and class-range
comparisons computed at analysis time, never from a model call. The
cautious-language requirement held up in practice on a genuinely weak-
signal case: EXP-003B's localization "miss" example was described as
*"the model found it statistically unremarkable relative to its
context"* rather than any claim the sentence is confirmed human —
demonstrating the template design correctly avoids overclaiming even
when applied to a low-confidence result, not just confident ones. This
is still a small, manual proof-of-concept (4 examples total, not an
implemented, general-purpose explanation system) — the "Implementation"
section below remains accurate that no such system has been built.

## Trade-offs

A fixed-template system is less flexible/eloquent than a generated
explanation would be — accepted, since faithfulness to actual measured
evidence is the explicit, non-negotiable requirement here (Section
12/13 of the brief), not fluency.

## Consequences

Positive: every explanation is auditable and reproducible; directly
testable (same input → same output, byte for byte).
Negative: template-writing is manual, ongoing work as new features are
added or refined (DEC-014's Revisit When) — not automated.

## Revisit When

1. Once EXP-003 determines which features actually carry signal
   (DEC-014), write templates only for the features that survive that
   filter — do not write explanation templates for a feature already
   shown to have no signal.
2. If normalization needs recalibration (e.g. after PRIMARY-DATASET-v1
   is superseded by a larger v2), the stored reference distributions
   this pipeline depends on need to be recomputed — not silently reused
   across dataset versions.

## Implementation

Not yet implemented — no explanation system exists yet. Depends on
EXP-003's feature-signal results (DEC-014) to know which templates are
worth writing first.

## Tests / Experiments

Not yet — pending implementation. When built: determinism tests (same
input → same explanation text) and a check that no code path in this
module calls a generative model.
